## 1. PURPOSE AND OBJECTIVES

Kontrak ini menetapkan persyaratan teknis, batas kewenangan, prosedur audit, standar keselamatan, dan kriteria penerimaan bagi Developer yang mengerjakan rancangan Control Plane Nusantara.

Tujuan utama adalah merancang mekanisme operasional terkontrol untuk:

1. Memeriksa kondisi API Service dan Console.
2. Memvalidasi konfigurasi, identitas build, serta kesiapan service sebelum restart.
3. Meminta persetujuan operator yang berwenang.
4. Melakukan restart API Service melalui mekanisme pengelola proses yang sah.
5. Memverifikasi pemulihan backend sebelum Console dimuat ulang.
6. Mencatat seluruh tahapan, keputusan, hasil, dan kegagalan.
7. Menyediakan prosedur pemulihan jika service gagal kembali beroperasi.

Seluruh pekerjaan harus mempertahankan arsitektur Nusantara yang sudah ada, melindungi perubahan pengguna, dan tidak menduplikasi engine atau mekanisme pengelolaan yang telah tersedia.

## 2. GOVERNING PRINCIPLES

Developer wajib mematuhi prinsip berikut.

### 2.1 V1-First Engineering

* Stabilitas dan penerimaan V1 merupakan prioritas utama.
* Kontrak API V1 yang sudah ada tidak boleh diubah tanpa otorisasi terpisah.
* Pekerjaan Control Plane tidak boleh digunakan sebagai alasan untuk memperluas V2.
* Setiap risiko terhadap V1 harus diidentifikasi sebelum perubahan diusulkan.

### 2.2 Audit Before Implementation

* Inventarisasi source, konfigurasi, kontrak, dan mekanisme runtime sebelum menyusun implementasi.
* Gunakan dokumentasi dan komponen yang sudah ada sebagai sumber kebenaran utama.
* Jangan menyimpulkan bahwa suatu fitur belum tersedia hanya karena belum ditemukan pada pemeriksaan pertama.
* Semua temuan harus memiliki bukti yang dapat diperiksa ulang.

### 2.3 Preserve Existing Work

Developer dilarang melakukan tindakan destruktif terhadap repositori.

Dilarang tanpa persetujuan eksplisit:

* Menghapus atau menimpa perubahan pengguna.
* Menjalankan `git reset --hard`, `git clean`, checkout destruktif, atau perintah sejenis.
* Menghapus database, data runtime, konfigurasi, atau artefak.
* Membuat duplikasi konfigurasi, engine, supervisor, atau kontrak.
* Mengganti arsitektur yang sudah berjalan hanya untuk menyederhanakan implementasi.

### 2.4 Human-Controlled Operations

Restart adalah tindakan operasional yang dapat mengganggu layanan. Tindakan tersebut harus berada di bawah otorisasi manusia, dengan target yang jelas, konfirmasi, batas waktu, audit trail, dan mekanisme pemulihan.

Tidak boleh ada restart otomatis yang aktif pada tahap audit ini.

## 3. SCOPE OF WORK

### 3.1 In Scope — Audit and Design

Developer diizinkan melakukan pemeriksaan baca-saja untuk:

* Memetakan entry point aplikasi dan router Control Plane.
* Mengidentifikasi mekanisme startup, shutdown, restart, dan supervisi proses.
* Memetakan API Service, Console UI, static assets, dan jalur komunikasi.
* Menginventarisasi endpoint diagnostik dan health check yang tersedia.
* Memeriksa autentikasi, otorisasi, pembatasan akses, serta audit logging.
* Mengidentifikasi risiko restart, konflik port, proses ganda, dan kegagalan pemulihan.
* Membandingkan source di disk dengan informasi runtime yang sudah tersedia.
* Menyusun rancangan kontrak, alur kerja, threat model, dan kriteria penerimaan.
* Memberikan rekomendasi implementasi berdasarkan bukti.

### 3.2 Out of Scope — Until Separately Authorized

Hal-hal berikut belum diizinkan:

* Mengedit atau membuat file proyek.
* Menambah, menghapus, atau mengubah endpoint operasional.
* Menjalankan restart, stop, start, reload service, atau tindakan setara.
* Mengubah konfigurasi, environment variables, atau process supervisor.
* Mengaktifkan fitur restart dari UI.
* Menjalankan migrasi, deployment, commit, push, atau release.
* Melakukan pengujian yang mengubah state atau mengganggu service aktif.
* Mengaktifkan agent otonom yang dapat memodifikasi atau mengoperasikan runtime.
* Mengubah kontrak V1 atau memajukan pekerjaan ke V2.

Pekerjaan di luar lingkup wajib diajukan sebagai proposal perubahan dan menunggu persetujuan.

## 4. REQUIRED ENGINEERING WORKFLOW

### Phase A — Repository and Runtime Inventory

Developer harus:

1. Mengidentifikasi entry point dan komposisi aplikasi.
2. Memetakan router dan kontrak Control Plane yang sudah ada.
3. Mengidentifikasi pemilik lifecycle proses.
4. Menentukan apakah Console merupakan UI pada backend yang sama atau aplikasi terpisah.
5. Memeriksa dokumentasi dan mekanisme keamanan yang sudah tersedia.
6. Mencatat batasan pemeriksaan runtime dan source.

**Deliverable:** `NUSANTARA-SERVICE-LIFECYCLE-AUDIT.md`

**Acceptance condition:** Semua kesimpulan penting memiliki bukti source atau observasi yang relevan; hal yang belum diketahui ditandai secara eksplisit.

### Phase B — Architecture and Contract Design

Developer harus merancang:

1. Batas tanggung jawab Control Plane UI.
2. Batas tanggung jawab Action Coordinator.
3. Hubungan dengan supervisor proses yang sudah tersedia.
4. Kontrak preflight dan persetujuan operator.
5. Kontrak restart dan pemantauan pemulihan.
6. Kontrak Console reload.
7. Format hasil operasi dan audit trail.
8. Kebijakan timeout, idempotensi, kegagalan, dan pemulihan.

**Deliverable:** `NUSANTARA-CONTROL-PLANE-RESTART-CONTRACT.md`

**Acceptance condition:** Tidak ada komponen yang memiliki tanggung jawab tumpang tindih tanpa alasan arsitektural yang terdokumentasi.

### Phase C — Security and Recovery Design

Developer wajib mengevaluasi:

* Autentikasi dan otorisasi operator.
* Pembatasan akses jaringan dan origin.
* Perlindungan terhadap CSRF dan pemanggilan mutasi tanpa izin.
* Larangan eksekusi shell command bebas dari browser.
* Validasi identitas proses dan target operasi.
* Penanganan request ganda.
* Timeout dan batas percobaan restart.
* Audit trail yang tidak membocorkan rahasia.
* Kegagalan supervisor atau backend.
* Prosedur pemulihan dan keputusan eskalasi kepada manusia.

**Deliverables:**

* `NUSANTARA-RESTART-SECURITY-THREAT-MODEL.md`
* `NUSANTARA-RECOVERY-AND-CONSOLE-RELOAD-PLAN.md`

**Acceptance condition:** Risiko kritis memiliki kontrol mitigasi, penanggung jawab, dan kriteria verifikasi yang jelas. Risiko yang belum dimitigasi harus dinyatakan sebagai blocker.

### Phase D — Audit Review and Authorization Gate

Sebelum implementasi, Developer harus menyerahkan:

* Ringkasan temuan audit.
* Daftar file yang diperkirakan perlu diubah.
* Dampak terhadap V1.
* Dependensi dan kebutuhan supervisor.
* Rencana pengujian.
* Rencana rollback.
* Risiko yang tersisa.
* Estimasi kompleksitas dan kebutuhan operasional.
* Daftar perubahan yang memerlukan persetujuan tambahan.

**Deliverable:** `NUSANTARA-CONTROL-PLANE-IMPLEMENTATION-PROPOSAL.md`

**Acceptance condition:** Proposal ditinjau dan disetujui secara eksplisit sebelum kode diubah.

Persetujuan audit tidak otomatis memberikan izin implementasi, restart, deployment, atau aktivasi runtime.

## 5. TARGET OPERATIONAL FLOW

Alur berikut merupakan rancangan target, bukan fitur yang sudah diimplementasikan.

1. **Observe:** baca status service, Console, konfigurasi, dan identitas build.
2. **Preflight:** validasi target, perubahan source, supervisor, konfigurasi, dan kesiapan pemulihan.
3. **Authorize:** minta persetujuan operator yang berwenang.
4. **Record:** buat operation ID dan catat permintaan yang disetujui.
5. **Restart:** delegasikan lifecycle operation kepada supervisor yang telah disetujui.
6. **Wait:** tunggu proses pulih dengan batas waktu yang ditetapkan.
7. **Verify:** periksa health, identitas build, endpoint yang diharapkan, dan hasil diagnostik.
8. **Reload Console:** hanya setelah backend lulus kriteria verifikasi.
9. **Report:** tampilkan hasil akhir, kegagalan, bukti, dan rekomendasi pemulihan.

Jika pemulihan gagal, sistem tidak boleh melanjutkan seolah-olah operasi berhasil. Console tidak boleh otomatis direload sebelum backend dinyatakan siap.

## 6. MANDATORY SAFETY GATES

| Gate                     | Persyaratan                                                   |
| ------------------------ | ------------------------------------------------------------- |
| SG-01 — Scope            | Tindakan sesuai lingkup dan otorisasi aktif                   |
| SG-02 — Preservation     | Perubahan pengguna dan data terlindungi                       |
| SG-03 — Identity         | Target proses dan service teridentifikasi dengan benar        |
| SG-04 — Authorization    | Persetujuan operator tervalidasi                              |
| SG-05 — Preflight        | Konfigurasi dan mekanisme pemulihan siap                      |
| SG-06 — Lifecycle        | Supervisor yang berwenang telah diidentifikasi                |
| SG-07 — Recovery         | Timeout, kegagalan start, dan eskalasi dirancang              |
| SG-08 — Verification     | Kriteria health, build, dan route ditentukan                  |
| SG-09 — Audit            | Semua keputusan dan hasil dapat ditelusuri                    |
| SG-10 — V1 Compatibility | Tidak ada regresi atau perubahan kontrak V1 tanpa persetujuan |
| SG-11 — Approval         | Implementasi menunggu otorisasi terpisah                      |
| SG-12 — Activation       | Aktivasi runtime menunggu otorisasi operasional terpisah      |

Setiap gate memiliki status `PASS`, `FAIL`, `NOT_VERIFIED`, atau `NOT_APPLICABLE` dengan alasan dan bukti.

Gate wajib yang `FAIL` atau `NOT_VERIFIED` tidak boleh dianggap lulus melalui asumsi.

## 7. TESTING AND VERIFICATION REQUIREMENTS

Setelah implementasi memperoleh otorisasi tersendiri, Developer harus mengusulkan pengujian berjenjang:

1. Unit tests untuk validasi kebijakan dan state transition.
2. Contract tests untuk request, response, error, dan otorisasi.
3. Security tests untuk akses tidak sah dan pemanggilan berulang.
4. Failure simulations untuk timeout, supervisor gagal, dan backend tidak sehat.
5. Integration tests pada lingkungan yang terkontrol.
6. Operational acceptance tests untuk alur restart dan Console reload.
7. Regression tests yang relevan terhadap V1.
8. Verifikasi bahwa audit trail dan pemulihan bekerja sesuai kontrak.

Pada tahap kontrak ini, pengujian yang mengubah state, mematikan proses, atau memengaruhi runtime tidak diizinkan.

Hasil pengujian harus menyertakan perintah, hasil aktual, lingkungan, dan bukti. Tes yang dilewati, tidak dijalankan, atau belum diverifikasi tidak boleh dilaporkan sebagai lulus.

## 8. ENGINEERING QUALITY REQUIREMENTS

Implementasi di masa mendatang wajib memenuhi prinsip berikut:

* Perubahan minimal dan terfokus.
* Tidak ada duplikasi supervisor atau sumber konfigurasi.
* Error handling eksplisit dan konsisten.
* Tidak ada klaim keberhasilan sebelum operasi benar-benar diverifikasi.
* Tidak ada rahasia pada log atau respons publik.
* API yang berpotensi memutasi state memiliki otorisasi dan audit.
* Operation ID, idempotensi, dan batas waktu ditentukan secara jelas.
* Observabilitas memadai untuk mendiagnosis kegagalan.
* Dokumentasi diperbarui bersama implementasi yang disetujui.
* Rollback tidak boleh menghapus perubahan pengguna yang sudah ada.

## 9. REQUIRED REPORTING FORMAT

Setiap laporan Developer wajib mencakup:

* Contract ID dan versi.
* Waktu pemeriksaan.
* Mode kerja yang dijalankan.
* Scope dan batas pemeriksaan.
* File atau endpoint yang diperiksa.
* Bukti yang ditemukan.
* Temuan positif dan negatif.
* Temuan yang belum diverifikasi.
* Risiko dan tingkat keparahan.
* Dampak terhadap V1.
* Rekomendasi dan alasan teknis.
* Status seluruh safety gates.
* Daftar perubahan yang diusulkan, bila ada.
* Konfirmasi bahwa tidak ada tindakan di luar kewenangan.

Status laporan harus menggunakan salah satu nilai berikut:

* `AUDIT_IN_PROGRESS`
* `AUDIT_COMPLETE_WITH_GAPS`
* `AUDIT_COMPLETE_READY_FOR_REVIEW`
* `BLOCKED`
* `APPROVAL_REQUIRED`

`AUDIT_COMPLETE_READY_FOR_REVIEW` berarti dokumen siap ditinjau, bukan berarti implementasi disetujui.

## 10. CHANGE AUTHORIZATION POLICY

Setiap perubahan wajib melewati pemisahan otorisasi:

| Authorization                                 | Status saat ini |
| --------------------------------------------- | --------------- |
| Audit source dan dokumentasi secara baca-saja | Diizinkan       |
| Membuat atau mengubah file proyek             | Tidak diizinkan |
| Menjalankan mutasi API atau restart           | Tidak diizinkan |
| Mengubah supervisor atau konfigurasi          | Tidak diizinkan |
| Menjalankan tes yang mengubah state           | Tidak diizinkan |
| Commit, push, deployment, atau release        | Tidak diizinkan |

Permintaan perubahan harus menyebutkan scope, file yang terdampak, risiko, metode verifikasi, dan rencana pemulihan.

Persetujuan untuk satu tindakan tidak berlaku otomatis untuk tindakan lain. Tidak boleh ada perluasan scope secara diam-diam.

## 11. FINAL ACCEPTANCE CRITERIA

Kontrak pekerjaan audit dapat ditutup jika:

* [ ] Inventarisasi lifecycle service selesai.
* [ ] Arsitektur Console dan backend telah dipetakan.
* [ ] Kontrak Control Plane telah disusun.
* [ ] Threat model telah ditinjau.
* [ ] Rencana recovery telah disusun.
* [ ] Semua safety gates memiliki status dan bukti.
* [ ] Dampak terhadap V1 terdokumentasi.
* [ ] Semua risiko kritis memiliki mitigasi atau blocker yang eksplisit.
* [ ] Proposal implementasi telah diserahkan untuk persetujuan.
* [ ] Tidak ada perubahan kode atau tindakan runtime tanpa otorisasi.

Penutupan audit tidak berarti Control Plane sudah berfungsi. Implementasi dan aktivasi memiliki acceptance gate tersendiri.
