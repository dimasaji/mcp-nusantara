## 1. Decision

**NO_EXISTING_TRUSTED_BOUNDARY — AUTHENTICATION_ARCHITECTURE_REQUIRED.**

Within the inspected Nusantara application, Control Plane and security integration, no existing boundary proves that an HTTP/browser caller is an authorized human operator before using the server-side admin credential. A new NORMAL caller-authentication architecture, or evidence of an already deployed external authenticated boundary, is required. It is not implemented or selected here.

Existing admin credential verification and OS peer attribution are reusable security primitives, not an established browser-authenticated transport. The conclusion is bounded to observed source. No claim is made that an unknown external deployment cannot provide identity; such deployment was neither evidenced nor assumed.

## 3. Existing Trusted Boundary

**None found that meets the complete requested browser-to-NORMAL path.**

`LocalOperatorChannel` is explicitly constructed, requires an operator policy, and is not auto-started. `peer()` obtains the OS named-pipe peer PID, impersonates to inspect the peer token, reverts impersonation, checks the policy and correlates the actual process actor. `serve_authenticated_once()` mints an internal VerifiedPeer only after native proof. These controls are source observations, not fresh OS/IPC test results.

The discovered consumer is `RuntimeAuthorization`, which checks private proof identity/policy, rejects replay, and validates bounded R2 operation bodies. `serve_operator_once` explicitly includes no listener creation, activation or startup loop. `app/main.py:95+` installs this foundation only in ATTESTATION. Neither `control-plane/src/api.ts` nor the Vite proxy connects browser requests to that native channel. Reusing the primitive for NORMAL would require a separately approved request-to-operator binding and lifecycle design; this task neither reuses nor activates R2 authority.

`control-plane/vite.config.ts:9` is a development transport proxy for `/v1/control-plane` and `/health`, not an authenticated BFF. Its loopback bind and fixed upstream do not identify a human. `app/main.py` is an API/legacy UI composition, not an existing authenticated React Control Plane BFF.

Deployment-related filenames (`Dockerfile`, `docker-compose.yml`, `docker-compose.audit.yml`) were observed, but filenames do not prove authenticated deployment. Secret-bearing deployment/environment contents, active processes and external proxy configuration were not inspected. Source searches in current application/security/scripts/frontend found no integrated browser OS identity provider or server-authenticated session for this path. This is a bounded source search, not exhaustive proof about the machine or external infrastructure.

## 4. Browser Identity Evidence

Available: browser review state, HTTP origin/host checks, local transport configuration and untrusted intention. Missing: independently verified human principal plus operation-specific binding for the browser request.

Required distinction:

```text
Caller authentication: verified principal / allowed preview caller — NOT_ESTABLISHED

Admin credential: backend access credential — value and availability NOT_OBSERVED
Review session: client UI acknowledgment/results — untrusted for authentication
ATTESTATION intention: PENDING request — untrusted, no NORMAL authority
```

An OS account running the server, the ability to connect to localhost, or a browser PID would not by themselves prove that the authenticated human requested this exact goal. No human identity was inferred from expected paths, process ownership, historical tests or client JSON.

## 5. Server Credential Ownership

Observed interface: the existing backend `require_admin` reads its configured server-side credential when actually invoked. This function was not invoked here. Actual credential value, availability, provisioning, owner process environment and deployment ownership are NOT_OBSERVED.

A future approved boundary must name its credential-use owner and verify the caller before that owner uses the existing credential. It must preserve backend `require_admin`, keep the actual credential out of frontend source/environment/storage/cookies/responses/logs, and avoid creating/copying/rotating/provisioning a secret as an incidental transport fix.

Simply injecting the server credential into every browser request would turn the proxy into a confused deputy: the backend would see a valid admin credential while the initiating human remained unproved. This is explicitly rejected.

## 6. Transport Boundary

Conceptual target only:

```text
Browser goal/session → verified permitted caller (MISSING)
 → trusted server-side fixed preview ingress (NOT_IMPLEMENTED)
 → existing server credential owner (delivery owner NOT_ESTABLISHED)
 → existing backend require_admin
 → future POST /v2/dev/inspection-preview (NOT_IMPLEMENTED)
 → terminal genuine DevCore inspection_preview → browser review → STOP
```

Minimum future constraints: single allowlisted POST/path and fixed local backend destination; bounded goal/session-only body; reject extra execution/write/authorization/toggle/upstream fields; no arbitrary target/header forwarding, credential redirects, retry or general `/v2/dev` fallback; validate and redact bounded response/error projection. Session_id is correlation only. No source resolution, tools, model/provider, database or lifecycle calls in the preview branch. Caller permission for preview cannot become general admin execution authority.

Current frontend proxies no `/v2` path; source CORS permits ports 3000/8000 but not configured Control Plane 5173. A future same-origin BFF could make its backend leg server-to-server without browser CORS expansion, but no such authenticated ingress is established. Direct browser-to-backend access from 5173 needs a separately authorized CORS decision under governing transport contract §16 and still does not solve identity/credential delivery. Backend hosting/composition changes also require separate authorization. No CORS/composition change is made here.

## 9. Security Risks

Unverified local browsers/processes borrowing server admin authority; cross-site requests and DNS rebinding; request identity confused with origin or session_id; replay/stale OS evidence; mixing ATTESTATION/native decision authority with NORMAL preview; broad proxy/redirect/header forwarding; token leakage through frontend builds, cookies, storage, traces/errors; silently executing general `/v2/dev` when preview is unavailable.

Conceptual alternatives, **no automatic selection, no new token/cookie/session/protocol designed or implemented**:

1. **An existing externally managed authenticated server/deployment boundary**, if the human can identify and authorize its inspection. It would need evidence of verified principal, allowed preview callers, trusted server credential ownership, fixed-route forwarding and fail-closed request handling. Such boundary is not found/proven in this repository inspection. If none already exists, creating one is a new authentication architecture requiring separate authorization.
2. **A new NORMAL native operator-to-request binding architecture using the existing OS-attribution primitive.** A future separately approved design would have to establish how a genuine human/operator proof authorizes the exact browser goal/request, prevents replay and keeps credential use server-side. Named-pipe process proof alone is insufficient. No bridge, activation, browser capability, cookie/session or R2 owner reuse is chosen here; whether this can safely satisfy the constraints remains a future design question.

Rejected alternative: attach the admin token solely because caller is localhost/same-origin or has checked a review box. That is an access expansion, not authentication reuse.
