# Existing audit/approval reuse and ownership

Recommendation: one ATTESTATION-local composition owner holds exactly one existing AuditTrail(path=None) and ApprovalQueue(audit=that_instance). Both remain application-process memory only; no production audit file, SQLite, WAL/SHM, RAG or new persistence path. NORMAL keeps its current v2 AuditTrail/ApprovalQueue objects and behavior unchanged. Mutually exclusive profile compositions reuse the same existing classes; no parallel audit implementation, hash-chain format, subsystem or generic governance service is introduced.

Future app.main composition creates this owner only when the approved ATTESTATION identity adapter is enabled. No instantiation occurs here. Do not import app.api.v2_routes or extract/alter its NORMAL behavior to obtain its globals. One worker/process is mandatory. No process restart restores grants, sessions or decisions; startup is DISARMED. Retain bounded pending reviews/events for the process lifetime and refuse additional review creation when capacity is exhausted, rather than silently dropping audit events. Capacity proposal: 32 review objects, 1024 audit events. Invalid-client attempts must not be able to fill the governance ledger before identity validation.

Audit ownership is private. Do not expose mutable entries or ApprovalRequest references to HTTP/UI callers. Queue.get() returns a mutable object and AuditTrail.entries() is only a shallow copy, so the adapter must return immutable projections and retain the authoritative frozen binding separately. Only the single owner may modify or consume queue state.

Reuse existing queue transitions. APPROVE maps to approved; REJECT maps to rejected. HOLD maps to request_changes plus explicit canonical HOLD event; ABORT maps to rejected plus explicit canonical ABORTED event when still pending. After approval/consumption, adapter terminal state plus permit abort handles HOLD/ABORT; never reinterpret queue CONSUMED as a successful generation. Do not change the existing NORMAL queue's enums or approval semantics. A fresh human review uses a fresh ID; no automatic reapproval or permit rearm.

Audit fields must record authoritative actor reference, logon-session reference, canonical action, subject, scope, reason, server UTC time, evidence/test references, runtime tuple, approval/decision ID and result. Service requester is a distinct server identity, not the human reviewer. Memory-only records are intentionally not durable compliance evidence. If durability is required, STOP for an approved existing sink/ownership decision; do not silently add a JSONL destination.

## Redaction and failure boundary

Existing redact() removes secret-like keys, replaces 16 consecutive decimal digits anywhere in strings, and truncates deep structures. It can alter opaque IDs/hashes and authorization-named fields. Do not disable redaction or change its global behavior. Proposed audit projection is shallow, credential-free, with explicit allowlisted non-secret keys. Encode digests/opaque numeric runs in reversible short groups separated by punctuation, and test exact round-trip integrity. Raw canonical binding remains frozen in memory; its encoded digest joins it to the redacted audit projection.

ApprovalQueue snapshots also pass through redaction. In this memory-only lifetime the original payload_hash remains in the queue object; do not reconstruct decisions from redacted snapshots or claim durable replay support. Before any grant, verify that the audit chain and required projected identity/binding/result fields survived redaction and match authoritative memory. If any binding is lossy, refuse authorization. Do not treat audit.verify() alone as complete semantic evidence.

Queue submit/decide/consume perform multiple audit operations; they are not a transaction spanning the runtime permit. Under a single governance lock, complete decision validation, queue consumption and semantic audit validation before grant. Any exception poisons that review terminally; no automatic retry. If a post-grant audit operation fails, invalidate the ARMED permit through the proposed abort primitive, clear server-held token and record failure if possible. No dispatch while audit/owner state is uncertain.
