## Requirement findings

### S-01 review approval is not a universal prerequisite for indexing or operator retrieval

Requirement: DOCX section 6 upload -> Docling -> review -> approval -> save -> index -> retrieval; FR-05/06/07 and Integrity NFR. Evidence: `engine.py:230-295` saves the original and ingests into active RAG before any review; `sop_review.py:68-71` review requires indexed document. `security/v1_knowledge.py:38-49` only enrolled pilots require Aktif, and :51-52 filters only pilot documents. First enrollment occurs via review GET (`knowledge_pipeline.py:44`) or trial session (`sop_review.py:174-175`), not upload. `tests/test_knowledge_pipeline_api.py:98-115` explicitly expects immediate READY and indexed count on upload. Static conclusion: current workflow differs from PRD ordering and permits retrieval of non-pilot uploads before review in the authenticated operator path. This is not a claim public users can read internal knowledge; public boundary returns no evidence. Priority P1. Impact: review gate meaning depends on enrollment; operator can retrieve before review, and an unapproved active index cannot be called an approved-only index. Recommendation after approval: define explicit staging/publication state and enforce the selected publication invariant across all retrieval paths while retaining V1 owner. Primary auditor should reproduce using isolated fixture through existing public APIs before marking behavioral FAIL.

### S-02 approval version omits Docling extraction identity

Requirement: FR-04/05 and Integrity NFR (approval bound to content version). Evidence: `sop_review.py:97-98` version hashes title, original extracted doc.source, PDF digest and source_pages; :119-124 approval binds trial and review event IDs. `document_tools.py:112` separately keys extraction by parser/config; :157-165 stores newly processed blocks under the unchanged review version. `SOPReview.detail` does not bind a specific extraction job/cache key/payload hash. `control-plane/e2e/docling-live.spec.ts` reprocesses and asserts approval unchanged. Static risk: changed parser/config/normalized blocks can become Chat context under an existing approved version without requiring renewed review. Priority P1. Impact: content approval may not describe actual extracted content used by Chat. Recommendation: bind substantive extraction identity and regression evidence to approval or document invariant that makes reprocessing content-equivalent; require fresh review when identity changes. No reproduction or actual approval mutation performed by this agent; root cause of historic 500 remains unknown.

### S-03 review/status GET routes mutate storage

Requirement: audit read-only/no database mutation constraint; FR-10/12, Integrity/Observability. Evidence: `knowledge_pipeline.py:43-44` constructs SOPReview then enrolls; `sop_review.py:56-65` DDL, :215 INSERT pilot; `document_tools.py:54` status updates expired jobs to FAILED. `engine.py:116-135` first pipeline access creates schema/config and marks PROCESSING interrupted. Thus merely visiting review/status can change gates/jobs. Priority P1 for audit safety and state semantics. Impact: read-only runtime audit using those GET endpoints violates the user's data-change boundary and can change document availability. Recommendation: audit existing data with true read-only SQLite mode; separate maintenance and enrollment writes into explicit actions after design approval. This is a source-demonstrated side effect, not a recreated production failure.

### S-04 detailed health contains unprobed availability claims

Requirement: FR-10 status accurate without mock status. Evidence: `routes.py:991-1005` returns every component as constant "available" (knowledge, workflow, policy, trust, memory, tools, MCP etc.) without per-component probes in this handler. Separate model verification fields are explicitly NOT_VERIFIED/inventory-only. Current Settings uses `/health` and warns it does not prove inference, which narrows the UI impact. Priority P2. Impact: consumers of `/v1/health/detail` can mistake module presence for runtime health. Recommendation: report NOT_TESTED/unknown or actual probe-derived status; do not infer a module is broken from constant status alone.

### S-05 new Hermes ACP integration is connection-only

Requirement: audit 002 Hermes -> task -> execution -> evidence; baseline section 4 integration planned. Evidence: `developer_core/hermes_acp_connection.py:1,32-36` initialize-only, task_execution_enabled false, CONNECTION_ONLY; `control-plane/src/hermes-connection.tsx:71` explicitly says tasks/tools/cost/history not integrated. API `/v1/control-plane/hermes/connection` (`control_plane.py:482,489`) reads/probes connection only. Priority P2 as deferred capability gap, not missing core orchestrator. Impact: successful connection cannot establish task execution/evidence capability. Recommendation: mark new integration HOLD/deferred under baseline and require separate operator scope before implementation. Core Hermes remains wired through `routes.py:1234-1236` -> `HermesAgent.execute_v1`, so no claim Hermes core is absent.
